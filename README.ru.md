# PygamE

Небольшой компонентный 2D-движок на Pygame, построенный по модели
GameObject/Component (как в Unity). Каждый объект в игре — это
`GameObject` с `Transform`; поведение (рендер, физика, ввод, анимация,
UI, звук, слежение камеры и т.д.) добавляется через прикрепление
`Component`.

Этот документ — полный, файл-за-файлом справочник: для каждого файла
движка объясняется, за что он отвечает, разбирается каждая функция/класс,
которые он определяет, и приводится рабочий пример. Он длинный намеренно
— прочитайте один раз от начала до конца, а потом используйте как
справочник.

## Быстрый старт

```bash
pip install -r requirements.txt
python main.py
```

Управление в демо: **A/D** или **←/→** — движение, **Space** — прыжок
(двойной прыжок — нажмите ещё раз в воздухе), **F1** — отладочная
панель, **F2** — контуры коллайдеров, **F3** — координатная сетка мира.

## Общая картина

**`GameObject`** — это именованная коробка со списком **`Component`** и
больше ничем. Он не умеет сам себя рисовать, падать под гравитацией или
реагировать на нажатия клавиш — всё это поведение целиком приходит от
того, какие компоненты к нему прикреплены. **`Scene`** хранит список
GameObject и управляет ими: каждый кадр вызывает `update()` на каждом,
обрабатывает пересечения триггеров, затем рисует мир (со смещением от
активной камеры) и UI (всегда в чистых экранных координатах, поверх
всего). **`Engine`** владеет самим окном и циклом, который каждый кадр
запускает `Scene.update()`/`render()`.

```
Engine.run()
  └─ каждый кадр:
       ├─ обработка событий, Input.update()
       ├─ Scene.update(delta_time)
       │    ├─ каждый активный GameObject.update(delta_time)
       │    │    └─ каждый включённый Component.update(delta_time), в порядке update_order
       │    └─ обработка пересечений триггеров (через spatial hash)
       └─ Scene.render(screen)
            ├─ мир: каждый SpriteRenderer, со смещением от активной Camera, с отсечением вне экрана
            └─ UI: каждый UIElement, в чистых экранных координатах, всегда поверх
```

Если держать эту схему в голове, каждый файл ниже — это ещё одна деталь
одной из коробок на этой картинке.

самостоятельно; `main.py` — единственный файл, который их связывает.

## Часть 1 - Основа: `engine/utils/`

Всё здесь имеет **нулевую зависимость от остального движка** — это
основание графа зависимостей.

### `engine/utils/vector2.py`

- **Ответственность:** Минимальный 2D-вектор, используется везде, где
  движку иначе пришлось бы передавать два отдельных float `x`/`y`.
- **Используется в:** `Transform` (position, scale), `Rigidbody2D`
  (velocity), `Camera` (математика позиции/смещения), `Scene` (смещение
  рендера).

```python
class Vector2:
    def __init__(self, x=0.0, y=0.0): ...
```

| Метод | Что делает |
|---|---|
| `copy()` | Новый, независимый `Vector2` с теми же x/y. |
| `as_tuple()` / `as_int_tuple()` | Обычный `(x, y)`, либо округлённый до int. |
| `Vector2.zero()` / `Vector2.one()` | Сокращения для `(0,0)` / `(1,1)`. |
| `length()` | Длина через `math.hypot`. |
| `normalized()` | То же направление, длина 1 (возвращает `(0,0)` для нулевого вектора, без деления на ноль). |
| `lerp(other, t)` | Линейная интерполяция, `t` ограничен диапазоном `[0, 1]`. |

Операторы: `+`, `-`, унарный `-`, `*`/`/` на скаляр, `+=`, `-=`, `==`.

```python
position = Vector2(100, 200)
velocity = Vector2(50, 0)
position += velocity * (1 / 60)   # сдвиг вправо на 50 пикс/сек за один кадр
```

### `engine/utils/warnings.py`

- **Ответственность:** Одна собственная категория предупреждений,
  `EngineWarning`, для отлова неправильной конфигурации *на этапе
  создания объекта* (неверная строка anchor, неизвестный
  `movement_type`) через стандартный модуль `warnings` Python — он сразу
  печатает точный файл/строку, где была допущена ошибка.
- **Используется в:** `BoxCollider2D`, `CircleCollider2D`,
  `SpriteRenderer` (неверные имена anchor), `PlayerController`
  (неизвестный `movement_type`), `UILayoutGroup` (неизвестный
  `direction`).

Это намеренно отделено от `DebugManager` (часть 13): предупреждение — это
*статическая* ошибка в вашем коде, отлавливаемая один раз, ещё до запуска
игры; `DebugManager` — для *runtime*-событий, которые стоит показывать на
игровом оверлее во время игры.

```python
class EngineWarning(UserWarning):
    """Вызывается через warnings.warn при неправильной конфигурации движка."""
```

### `engine/utils/anchors.py`

- **Ответственность:** **Единственная общая реализация** математики
  anchor'ов — используется в `SpriteRenderer`, `BoxCollider2D` и
  `CircleCollider2D`, так что все трое одинаково понимают, что значит
  `"center"` или `"bottomleft"`. См. [«Anchor'ы подробно»](#anchorы-подробно)
  — полную историю о том, зачем этот файл появился и что он исправил.

```python
VALID_ANCHORS = {
    "topleft", "midtop", "topright",
    "midleft", "center", "midright",
    "bottomleft", "midbottom", "bottomright",
}

def anchor_to_topleft_offset(anchor, width, height): ...
```

`anchor_to_topleft_offset(anchor, width, height)` возвращает `(dx, dy)`
такие, что `верхний_левый_угол = точка_anchor + (dx, dy)`, для фигуры
данного размера. Вычисляется через одноразовый `pygame.Rect` в начале
координат — точно для целочисленных размеров на всех 4 угловых и 4
средне-рёберных anchor'ах, и корректно в пределах собственного округления
pygame для `"center"` при нечётном размере.

```python
from engine.utils.anchors import anchor_to_topleft_offset
dx, dy = anchor_to_topleft_offset("center", 40, 60)  # (-20, -30)
```

### `engine/utils/spritesheet_loader.py`

- **Ответственность:** Загружает изображение spritesheet вместе с его
  JSON-атласом (например, экспортированным из TexturePacker) прямо в
  форму `{имя: [surface, ...]}`, которую ожидает `Animator`.
- **Зависит от:** `pygame` (изображение/subsurface), `DebugManager`
  (логирование ошибок).

```python
def load_spritesheet_animations(json_path, image_path): ...
```

Поддерживает оба распространённых формата атласа — объект `"frames"` с
ключами-именами файлов (`{"walk_00.png": {"frame": {...}}}`), либо массив
`"frames"` из объектов `{"filename": ..., "frame": {...}}`. Имена кадров
разбиваются на `(имя_анимации, номер_кадра)` через отсечение расширения
файла и любого завершающего числа — `"walk_01.png"` → `("walk", 1)` — и
кадры каждой анимации затем **сортируются по этому номеру**, а не по
тому, в каком порядке они перечислены в JSON (обычная алфавитная
сортировка поставила бы `"walk_10"` перед `"walk_2"` и молча перепутала
бы порядок анимации).

```python
from engine.utils.spritesheet_loader import load_spritesheet_animations
from engine.components.animator import Animator

animations = load_spritesheet_animations("assets/hero.json", "assets/hero.png")
hero.add_component(Animator(animations=animations, default_animation="idle"))
```

Пути используются точно как переданы (относительно текущей рабочей
директории, либо абсолютные) — та же конвенция, что и у самого
`pygame.image.load`. Ошибки (отсутствующий файл, некорректный JSON,
нераспознанный формат атласа) логируются через `DebugManager` с указанием
пути/шага, на котором произошёл сбой, а затем выбрасываются повторно —
отсутствующий ассет стоит увидеть сразу, а не молча продолжить работу с
наполовину загруженным spritesheet.

## Часть 2 - Ядро компонентной системы

### `engine/components/component.py`

- **Ответственность:** Базовый класс, от которого наследуется каждое
  поведение — определяет жизненный цикл `start()`/`update()` и
  `update_order`.
- **Используется:** везде.

```python
class Component:
    update_order = 0
    def __init__(self): ...
    def start(self): ...
    def update(self, delta_time): ...
```

| Член | Что делает |
|---|---|
| `update_order` (атрибут класса, по умолчанию `0`) | Перед вызовом `update()` каждый кадр `GameObject` сортирует свои компоненты по этому значению (по возрастанию). См. таблицу ниже для встроенных компонентов. |
| `game_object` | Обратная ссылка, устанавливается `GameObject.add_component()`. |
| `enabled` | `True` по умолчанию; `GameObject.update()` полностью пропускает `update()`, если `False`. |
| `start()` | Выполняется один раз, в момент, когда GameObject этого компонента попадает в работающую сцену. Безопасно вызывать более одного раза (приватный флаг делает каждый вызов после первого пустышкой). Переопределяйте это (не `__init__`), чтобы искать соседние компоненты. |
| `update(delta_time)` | Выполняется каждый кадр, пока включён/активен. `delta_time` — секунды с прошлого кадра. |

**Таблица `update_order`** (почему камера всегда видит *финальные*
позиции кадра, почему физика выполняется раньше всего, что на неё
реагирует):

| Компонент | update_order |
|---|:---:|
| `Rigidbody2D` | -100 |
| `BoxCollider2D` / `CircleCollider2D` | -90 |
| *(игровой код, UI, Animator, PlayerController)* | 0 |
| `Camera` | 100 |

```python
class SpinForever(Component):
    def __init__(self, degrees_per_second=90):
        super().__init__()
        self.degrees_per_second = degrees_per_second

    def update(self, delta_time):
        self.game_object.transform.rotation += self.degrees_per_second * delta_time
```

### `engine/components/transform.py`

- **Ответственность:** Позиция, поворот, масштаб — создаётся
  автоматически для каждого `GameObject`.

```python
class Transform(Component):
    def __init__(self, x=0.0, y=0.0, rotation=0.0, scale_x=1.0, scale_y=1.0): ...
```

| Член | Тип | Что делает |
|---|---|---|
| `position` | `Vector2` | Пиксели в мировых координатах. |
| `rotation` | `float` | Градусы, по часовой стрелке. Отрисовывается `SpriteRenderer` (часть 3). |
| `scale` | `Vector2` | `(1,1)` = исходный размер. Отрисовывается `SpriteRenderer`; **не** влияет на размер коллайдера (вызовите `set_size`/`set_radius` явно, если нужно их совместить). |
| `translate(dx, dy)` | | Сокращение для `position.x += dx; position.y += dy`. |

`GameObject.x`/`.y` остаются алиасами для `transform.position.x`/`.y`.

### `engine/core/game_object.py`

- **Ответственность:** Именованный контейнер компонентов плюс связующий
  код, который запускает `start()`/`update()` в чётко заданном порядке.

```python
class GameObject:
    def __init__(self, x=0.0, y=0.0, name="GameObject"): ...
```

| Член | Что делает |
|---|---|
| `transform` | Создаётся автоматически - всегда валиден. |
| `active` (свойство) | `False` полностью пропускает объект: `update()`, и каждый запрос `Scene.get_components()` (то есть и рендер, и коллизии). **Переключение уведомляет владеющую Scene** (`Scene._on_active_changed`), что сразу поддерживает кэш компонентов и spatial hash в актуальном состоянии — см. [Производительность](#производительность). |
| `scene` | Устанавливается `Scene.add_game_object()`. |
| `add_component(c)` / `get_component(cls)` / `get_components(cls)` / `remove_component(c)` | Стандартное управление компонентами; `add_component`/`remove_component` уведомляют сцену об инвалидации кэша компонентов. |
| `start()` / `update(delta_time)` | Запускает `start()`/`update()` каждого компонента, отсортированных по `update_order` (с кэшированием, пересортировка только при реальном изменении списка компонентов). |
| `x`, `y` | Алиасы для `transform.position.x`/`.y`. |

```python
enemy = GameObject(x=300, y=100, name="Slime")
rb = enemy.add_component(Rigidbody2D(gravity=900, use_gravity=True))
enemy.add_component(SpriteRenderer(sprite=slime_image))
enemy.active = False   # мгновенно исключается из update/render/коллизий, без удаления
```

## Часть 3 - Рендер

### `engine/components/sprite_renderer.py`

- **Ответственность:** Хранит изображение для отрисовки и (начиная с
  этого обновления) в какой точке этого изображения находится позиция
  transform'а.
- **Зависит от:** `Component`, `engine.utils.anchors` (общая математика
  anchor'ов).
- **Используется в:** `Scene._render_world()`.

```python
class SpriteRenderer(Component):
    def __init__(self, sprite=None, z_index=0, offset_y=0, anchor="topleft"): ...
```

| Член | Что делает |
|---|---|
| `sprite` | `pygame.Surface`, либо `None`, чтобы ничего не рисовать. Всегда *исходное*, неповёрнутое/немасштабированное изображение — `get_transformed_sprite()` ниже возвращает производное. |
| `anchor` | Какая точка спрайта находится в позиции transform'а — **те же 9 именованных anchor'ов и та же общая математика**, что и у `BoxCollider2D`/`CircleCollider2D`. Установите то же значение, что и у `anchor` вашего коллайдера, чтобы они визуально совпадали — см. [«Anchor'ы подробно»](#anchorы-подробно). Неверные значения вызывают предупреждение и откатываются на `"topleft"`. |
| `z_index` | Порядок слоёв, меньшее значение рисуется первым. |
| `offset_y` | Влияет только на *ключ сортировки* рендера (`position.y + offset_y`, для дешёвой имитации глубины), не на позицию отрисовки. |
| `set_sprite(sprite)` | Заменяет спрайт и сбрасывает кэш поворота/масштаба. |
| `get_anchor_offset()` | `(dx, dy)` от позиции transform'а до исходного верхнего левого угла спрайта, согласно `anchor`. `(0,0)`, если спрайта ещё нет. |
| `get_transformed_sprite(rotation, scale_x, scale_y)` | Спрайт, повёрнутый/масштабированный по этим значениям, **с кэшированием** по `(id спрайта, поворот, масштаб)`, так что статичный объект не пересчитывается каждый кадр. Поворот положителен по часовой стрелке (собственный `rotate()` pygame положителен против часовой — отсюда смена знака внутри). |

`Scene._render_world()` (часть 12) использует `get_anchor_offset()`, чтобы
найти исходный центр спрайта (неподвижную точку, вокруг которой вращается
и масштабируется спрайт), затем `get_transformed_sprite()` для реальной
поверхности для отрисовки — обычно вы не вызываете их сами, если только
не пишете собственный рендер.

```python
renderer = enemy.add_component(SpriteRenderer(sprite=slime_image, anchor="center"))
enemy.add_component(BoxCollider2D(size=slime_image.get_size(), anchor="center"))
# теперь оба согласны, что (enemy.x, enemy.y) — это ЦЕНТР слизня

enemy.transform.rotation = 45     # отрисовывается, поворот вокруг центра спрайта
enemy.transform.scale.x = 1.5     # отрисовывается, в 1.5 раза шире
```

## Часть 4 - Физика и столкновения

Здесь друг с другом работают четыре файла. Читайте их в этом порядке:
`collider2d.py` (общая, независимая от формы база) → `box_collider2d.py`
/ `circle_collider2d.py` (две конкретные формы) → `rigidbody2d.py` (то,
что реально двигается и разрешает столкновения) → `../core/spatial_hash.py`
(что делает проверку многих объектов быстрой).

### `engine/components/collider2d.py`

- **Ответственность:** Всё общее между `BoxCollider2D` и
  `CircleCollider2D`, что не зависит от конкретной формы — состояние
  триггера, списки колбэков `on_trigger_enter/stay/exit`, отслеживание
  пересечений и безопасная диспетчеризация.
- **Используется в:** `BoxCollider2D`, `CircleCollider2D` (оба наследуют
  от него), `Scene` (запрашивает `get_components(Collider2D)` для
  обработки триггеров и для отрисовки контуров в `DebugManager` — один
  запрос покрывает обе формы).

```python
class Collider2D(Component):
    shape = None  # "box" или "circle" - задаётся подклассами
    def __init__(self, is_trigger=False): ...
```

| Член | Что делает |
|---|---|
| `is_trigger` | `False` = твёрдый (только `BoxCollider2D` разрешается как твёрдый в `Rigidbody2D` — см. ниже). `True` = только пересечение. |
| `on_trigger_enter` / `_stay` / `_exit` | Списки `callback(trigger, other)`. Добавляйте через `.append()`. |
| `overlapping_colliders` (свойство) | Снимок только для чтения того, с чем этот триггер сейчас пересекается. |
| `overlaps(other)` | Абстрактный - каждый подкласс реализует свою точную проверку формы-к-форме, диспетчеризуя по `other.shape` (строке), а не через `isinstance`, специально чтобы `box_collider2d.py` и `circle_collider2d.py` никогда не импортировали друг друга. |
| `check_trigger_events(other)` | Сравнивает результат `overlaps()` этого кадра с состоянием прошлого кадра и вызывает нужный список колбэков. Вызывается `Scene`, обычно не вами напрямую. |
| `_sync_spatial_hash()` | Вызывается каждым подклассом в конце обновления своей формы — см. [Производительность](#производительность). |

Здесь же живут две свободные функции, общие для реализаций `overlaps()`
обеих форм: `_circle_circle_overlap(...)` (расстояние между центрами
против суммы радиусов) и `_circle_rect_overlap(...)` (ближайшая точка
прямоугольника к центру круга — стандартный тест circle-vs-AABB).

### `engine/components/box_collider2d.py`

- **Ответственность:** Прямоугольный хитбокс.
- **Зависит от:** `Collider2D`, `SpriteRenderer` (авто-размер),
  `engine.utils.anchors`.
- **Используется в:** `Rigidbody2D` (единственная форма, с которой он
  разрешает твёрдые столкновения), демо-контент, игровые скрипты.

```python
class BoxCollider2D(Collider2D):
    def __init__(self, size=None, offset_x=0, offset_y=0, anchor="topleft", is_trigger=False): ...
```

**Размер:** указывайте `size=(w, h)` явно, когда возможно. Если
пропущено, размер измеряется *один раз* по спрайту при `start()` и затем
**фиксируется** — он больше никогда не меняется автоматически, даже если
спрайт позже поменяет размер (`Animator`, переключающий кадры). Это
намеренно: коллайдер, который продолжал переизмерять живой спрайт каждый
кадр — именно то, что вызывало сообщённый баг с дёрганием при
приземлении в более ранней версии (см. [«Что изменилось»](#что-изменилось-в-этом-обновлении))
— два кадра анимации, различающиеся по высоте всего на пиксель, заставляли
хитбокс заметно "прыгать" между размерами на каждом переходе анимации.
Вызовите `set_size(w, h)` для намеренного изменения размера (например,
приседания).

| Член | Что делает |
|---|---|
| `rect` | Текущий `pygame.Rect`, квантованный до пикселя (pygame округляет каждую координату). |
| `anchor` | Те же 9 имён, что и у `SpriteRenderer` — см. [«Anchor'ы подробно»](#anchorы-подробно). Неверные значения вызывают предупреждение и откат на `"topleft"`. |
| `set_size(w, h)` | Явно (пере)зафиксировать размер. |
| `snap_left_to` / `snap_right_to` / `snap_top_to` / `snap_bottom_to(coord)` | Сдвигает владеющий Transform так, чтобы этот край оказался ровно в `coord`, используя *точную вещественную* позицию transform'а, а не уже округлённый `.rect`. Именно это вызывает `Rigidbody2D` для разрешения столкновения — почему точность здесь важна, см. в разделе про Rigidbody2D ниже. |
| `overlaps(other)` | `rect.colliderect(other.rect)` для другого box; общий тест circle-rect для круга. |

```python
player.add_component(BoxCollider2D(size=(32, 48), anchor="topleft"))
coin_collider = coin.add_component(BoxCollider2D(is_trigger=True))
coin_collider.on_trigger_enter.append(lambda trigger, other: print("касание!"))
```

### `engine/components/circle_collider2d.py`

- **Ответственность:** Круглый хитбокс с *точной* проверкой пересечения
  circle-vs-circle и circle-vs-box — в отличие от приближения через
  ограничивающий прямоугольник по умолчанию в `create_circle()` (часть
  11), здесь проверяется истинное расстояние до центра.
- **Область применения - прочтите перед использованием:** **только
  обнаружение пересечения/триггера.** `Rigidbody2D` ищет только
  `BoxCollider2D` для разрешения твёрдых столкновений; `CircleCollider2D`
  всё ещё может двигаться (гравитация/скорость применяются к его
  Transform как обычно), но физически не толкает и не получает толчков.
  Для монетки, сенсора или радиуса обнаружения (почти всегда круглых,
  почти всегда триггеров) это именно то, что нужно. Для твёрдого
  катящегося шара, которому нужно физически отскакивать/останавливаться,
  этот движок пока такого не реализует — это естественная, документированная
  точка расширения (см. конец этого раздела).

```python
class CircleCollider2D(Collider2D):
    def __init__(self, radius=None, offset_x=0, offset_y=0, anchor="topleft", is_trigger=False): ...
```

| Член | Что делает |
|---|---|
| `radius` (свойство) | Только для чтения; задаётся через конструктор или `set_radius()`. |
| `center_x`, `center_y` | Реальный центр круга в мировых координатах (вычисляется из позиции transform'а + anchor + offset — см. ниже). |
| `rect` | Ограничивающий прямоугольник `pygame.Rect` вокруг круга — используется для broad-phase запросов и контура в `DebugManager`; **не** то, против чего проверяет `overlaps()`. |
| `anchor` | Те же 9 имён, применённые к ограничивающему квадрату круга `(диаметр, диаметр)`. Значение по умолчанию `"topleft"` совпадает со значением по умолчанию у `BoxCollider2D`/`SpriteRenderer`, поэтому круглый коллайдер по умолчанию корректно центрируется под `SpriteRenderer` по умолчанию (тоже `"topleft"`), показывающим круг, отрисованный по центру своей поверхности — почему это важно и что это исправляет, см. в [«Anchor'ы подробно»](#anchorы-подробно). |
| `set_radius(r)` | Явно (пере)зафиксировать радиус, та же идея, что и `BoxCollider2D.set_size()`. |
| `overlaps(other)` | Точный тест circle-circle или circle-rect, диспетчеризация по `other.shape`. |

```python
sensor_go = GameObject(x=200, y=200, name="PickupRadius")
sensor = sensor_go.add_component(CircleCollider2D(radius=80, is_trigger=True))
sensor.on_trigger_enter.append(lambda t, o: print("что-то вошло в радиус"))
```

*Расширение твёрдой физики кругов:* `Rigidbody2D._solid_colliders_near()`
(следующий раздел) фильтрует по `isinstance(c, BoxCollider2D)` — научить
его разрешать столкновения также с `CircleCollider2D` (разрешение
circle-vs-box через ближайшую точку, либо истинное circle-vs-circle для
двух круглых тел) — естественный следующий шаг для игры, которой нужны
физически катящиеся шары; это намеренно оставлено за пределами этого
прохода, чтобы не торопиться с новой математикой разрешения столкновений
именно в той области, которую было сложнее всего сделать правильно в
первый раз (см. [«Что изменилось»](#что-изменилось-в-этом-обновлении)).

### `engine/components/rigidbody2d.py`

- **Ответственность:** Гравитация + трение + реакция на столкновения AABB.
- **Зависит от:** `Collider2D`/`BoxCollider2D`, `DebugManager`
  (одноразовое предупреждение, если нет коллайдера), `Vector2`.
- **Используется в:** всё, что должно падать, двигаться под скоростью
  или физически сталкиваться.

```python
class Rigidbody2D(Component):
    GROUND_PROBE_DISTANCE = 4
    def __init__(self, gravity=500, gravity_scale=1.0, drag=0.0, mass=1.0,
                 use_gravity=True, is_kinematic=False, terminal_velocity=1000): ...
```

**Шаг физики, каждый кадр:** применить гравитацию к вертикальной скорости
→ ограничить `terminal_velocity` → применить `drag` к горизонтальной
скорости → сдвинуть по X, разрешить столкновения по X → сдвинуть по Y,
разрешить столкновения по Y. Полное разрешение одной оси перед другой —
стандартное упрощение AABB, избегающее неоднозначных случаев с
диагональными углами.

| Член | Что делает |
|---|---|
| `velocity` | `Vector2`, пикс/сек. |
| `velocity_x`, `velocity_y` | Алиасы-float для обратной совместимости. |
| `is_grounded` | `True`, пока объект стоит на чём-то твёрдом. Стабильно (не мерцает от кадра к кадру) — см. `GROUND_PROBE_DISTANCE` ниже. |
| `is_kinematic` | Двигается под собственной скоростью, игнорирует гравитацию/силы, никогда не толкается другими - для движущихся платформ. |
| `add_impulse(ix, iy)` | Мгновенно: `Δv = impulse / mass`. |
| `add_force(fx, fy, delta_time)` | Постоянно: `Δv = (force/mass) * delta_time` - вызывать каждый кадр. |
| `stop()` | Обнуляет скорость. |

**Почему коррекция столкновений теперь *точная* (не приближённая):**
`.rect` — это `pygame.Rect`, который округляет каждую координату до
ближайшего целого. Наивный подход — вычислить `overlap =
collider.rect.bottom - other.rect.top` (int), затем вычесть его из
*вещественной* позиции объекта — выглядит точным, но не является таковым:
округление при построении `.rect` теряет долю пикселя, которая не
компенсируется обратно, и за много кадров это превращается в заметное
дрожание. Вместо этого `_resolve_collisions_x/y` вызывает
`collider.snap_bottom_to`/`snap_top_to`/`snap_left_to`/`snap_right_to`,
которые пересчитывают скорректированную позицию напрямую из точной
вещественной позиции transform'а и точного края *другого* коллайдера —
полностью минуя эту потерю точности от округления. `.rect` всё ещё
используется для первичной проверки "есть ли вообще пересечение" (вопрос
да/нет, где квантование не важно), но никогда — для математики коррекции.

**Почему `is_grounded` не мерцает:** гравитация каждый отдельный кадр
подталкивает покоящееся тело вниз на долю пикселя (именно это заново
запускает проверку "всё ещё касается"), и то, округлится ли эта доля
`.rect` обратно в "всё ещё касается" или в "только-только оторвался",
меняется практически каждый второй кадр — без дополнительной обработки
это заставляло `is_grounded` (и всё, что его читает, например, какую
анимацию проигрывать) мерцать каждый кадр в покое. `_probe_for_ground()`
проверяет несколько пикселей ниже коллайдера (`GROUND_PROBE_DISTANCE`, по
умолчанию 4px), когда в этом кадре нет *прямого* пересечения, так что
покоящееся тело стабильно читается как стоящее на земле.

**`_solid_colliders_near(rect)`** — метод, который больше всего изменился
ради производительности в этом обновлении — см. [Производительность](#производительность)
о том, почему теперь он запрашивает `SpatialHash` сцены вместо перебора
всех коллайдеров в сцене, и почему это безопасно (никогда не устаревает в
пределах одного кадра, никогда не пропускает реальное пересечение).

```python
rb = player.add_component(Rigidbody2D(gravity=900, use_gravity=True, drag=3.0))
if rb.is_grounded:
    rb.add_impulse(0, -500)                    # прыжок
def apply_wind(delta_time):
    rb.add_force(200, 0, delta_time)           # вызывать каждый кадр для постоянного толчка
```

### `engine/core/spatial_hash.py`

- **Ответственность:** Равномерная сетка для быстрых broad-phase запросов
  "что рядом с этим rect" — см. [Производительность](#производительность)
  полную историю о том, зачем это нужно, и цифры замеров.
- **Используется в:** `Scene` (владеет одним экземпляром на сцену),
  `Collider2D` (регистрируется сам при обновлении своей формы),
  `Rigidbody2D` (запрашивает его вместо перебора всех коллайдеров).

```python
class SpatialHash:
    def __init__(self, cell_size=128): ...
    def update(self, collider): ...   # (пере)вставить, чтобы совпадало с текущим .rect
    def remove(self, collider): ...
    def query(self, rect): ...        # набор кандидатов broad-phase рядом с rect
    def clear(self): ...
```

`query(rect)` возвращает коллайдеры, разделяющие ячейку сетки с `rect` —
набор *кандидатов*, который может включать несколько ложных срабатываний
(но никогда не пропускает настоящее), что вызывающий код всегда
подтверждает точной проверкой `overlaps()` или `.rect.colliderect()`
после. Обычно вы не вызываете это напрямую — `Rigidbody2D` и
`Scene._process_triggers()` делают это за вас.

## Часть 5 - Анимация

### `engine/components/animator.py`

- **Ответственность:** Циклически меняет спрайт `SpriteRenderer` по
  списку кадров во времени.
- **Используется в:** `PlayerController` (вызывает `play()` каждый кадр с
  нужной анимацией под текущее состояние).

```python
class Animator(Component):
    def __init__(self, animations=None, default_animation=None, frame_duration=0.1): ...
```

`animations` — это `{"idle": [surf, ...], "jump": [surf, ...]}` — именно
то, что возвращает `load_spritesheet_animations()` (часть 1).

| Член | Что делает |
|---|---|
| `play(name, loop=True, reverse=False)` | **Безопасно вызывать буквально каждый кадр** с нужной анимацией — повторные вызовы с тем же, уже проигрываемым именем ничего не делают, кроме обновления `loop`/`reverse`. Сбрасывает на кадр 0 только когда имя реально меняется, или предыдущее проигрывание завершилось. (Более ранняя версия сбрасывала при *каждом* вызове независимо от этого, что означало — анимация, управляемая так (единственный способ, которым `PlayerController` вообще её вызывает), никогда не могла продвинуться дальше кадра 0.) |
| `pause()` | Останавливает продвижение, оставляя `frame_index` на месте. |
| `stop()` | Останавливает и сбрасывает на кадр 0. |
| `is_playing`, `frame_index`, `current_animation` | Состояние, доступное фактически только для чтения. |

```python
anim = player.add_component(Animator(
    animations={"idle": [idle_frame], "walk_right": [w1, w2, w3, w4]},
    default_animation="idle", frame_duration=0.12,
))
anim.play("walk_right")   # вызывать каждый кадр при ходьбе - продолжает нормально проигрываться
```

## Часть 6 - Система ввода

### `engine/input/key.py`

- **Ответственность:** Понятные имена для кодов клавиш pygame, и
  `normalize_key()`, превращающая любой из вариантов в исходный int.

```python
Key.W          # через атрибут
"w"            # строка, регистр не важен
pygame.K_w     # "сырая" константа pygame - Key.W буквально то же самое значение int
```

`Key` покрывает буквы, цифры (как `NUM_0`..`NUM_9` — `Key.0` не является
корректным синтаксисом Python, но строковая форма `"0"` работает
напрямую), стрелки, распространённые клавиши редактирования/пробела,
модификаторы и F1-F12. `normalize_key(key)` принимает любую из трёх форм
выше; для строки сначала проверяет небольшую таблицу алиасов (`"space"`,
`"left"`, `"shift"`, ...), затем откатывается на
`pygame.key.key_code(name)` — так что любое имя клавиши, которое знает
сам pygame, работает, даже если его нет в таблице алиасов. Выбрасывает
`ValueError` для нераспознанного значения, так что опечатка в имени
клавиши падает сразу, а не молча никогда не срабатывает.

### `engine/input/input_manager.py`

- **Ответственность:** Состояние клавиатуры и мыши, с определением
  "именно в этом кадре" поверх "сырого" состояния "зажато сейчас" от
  pygame.
- **Используется в:** `PlayerController`, `UIButton`, всё, что нуждается
  во вводе.

```python
class Input:
    def update(self): ...   # вызывается раз в кадр Engine, до Scene.update()
```

Та же схема двойного доступа, что и везде в движке, где нужна
доступность без протаскивания ссылки через каждый компонент:

```python
from engine.input.input_manager import Input
from engine.input.key import Key

Input.is_pressed(Key.W)             # зажато прямо сейчас
Input.is_just_pressed(Key.SPACE)    # true только в кадре самого нажатия
Input.is_just_released(Key.SPACE)

Input.mouse_position()              # (x, y) в экранных пикселях
Input.is_mouse_pressed(0)           # 0=левая, 1=средняя, 2=правая
Input.is_mouse_just_pressed(0)
Input.is_mouse_just_released(0)
```

`Engine.run()` вызывает `self.input.update()` каждый кадр, сразу после
обработки очереди событий pygame и до `Scene.update()` — так что всё, что
компонент читает во время своего `update()`, отражает состояние именно
этого кадра. Если вы сами управляете `Scene.update()` вне `Engine.run()`
(например, в тесте), вам тоже нужно самостоятельно вызывать
`Input.instance().update()`, по той же причине.

## Часть 7 - Управление персонажем

### `engine/components/player_controller.py`

- **Ответственность:** Превращает ввод в движение — top-down или
  платформер — и (если есть `Animator`) выбирает, какая анимация должна
  проигрываться.
- **Зависит от:** `Input`/`Key` (часть 6), `Animator`, `Rigidbody2D` (оба
  опциональны — см. ниже).

```python
class PlayerController(Component):
    def __init__(self, speed=200, jump_force=350, movement_type="top_down",
                 keybinds=None, anim_map=None,
                 coyote_time=0.1, jump_buffer_time=0.1, max_jumps=1): ...
```

**Режимы:** `"top_down"` (движение в 4/8 направлений, без гравитации —
нормализует диагональную скорость до скорости по осям) или
`"platformer"` (бег + прыжок через `Rigidbody2D`).

**Мульти-прыжок / двойной прыжок:** `max_jumps` — сколько раз персонаж
может прыгнуть, прежде чем снова коснуться земли — `1` (по умолчанию)
это обычный одиночный прыжок, `2` — двойной, и так далее. *Первый* прыжок
в цепочке всё ещё учитывает `coyote_time` (льготное окно после ухода с
платформы); каждый прыжок после первого доступен сразу в воздухе, так как
в этот момент игрок сознательно использует дополнительный прыжок, а не
случайно сходит с края платформы. Счётчик восстанавливается в момент,
когда `is_grounded` становится true. Читайте `controller.jumps_remaining`
для отображения в UI (см. `examples/scripts/jumps_hud.py`, часть 15).

**Буферизация прыжка:** `jump_buffer_time` — прыжок, нажатый чуть *до*
приземления, всё равно срабатывает в момент касания земли.

**`keybinds`** принимает `Key.*`/«сырые» `pygame.K_*`/строки
взаимозаменяемо (по умолчанию WASD + стрелки + Space):

```python
character.add_component(PlayerController(
    speed=200, jump_force=500, movement_type="platformer", max_jumps=2,
    keybinds={"left": ["a", Key.LEFT], "right": ["d", Key.RIGHT], "jump": [Key.SPACE]},
))
```

**Работает без Rigidbody2D или Animator** — оба опциональны; без
rigidbody движение откатывается на прямое перемещение transform'а (а
прыжок ничего не делает, с одноразовым предупреждением, если вы в режиме
`"platformer"`); без animator вызовы выбора анимации просто пропускаются.

**Расширение** — наследуйтесь и переопределяйте один хук, а не весь класс:

| Хук | Вызывается |
|---|---|
| `_on_jump()` | В момент срабатывания любого прыжка. |
| `_can_jump()` / `_wants_to_jump()` | Чтобы изменить, что считается "прыжок разрешён" - например, способность прыжка от стены. |
| `_play_platformer_animation()` / `_play_top_down_animation()` | Чтобы добавить состояния анимации. |
| `_read_move_axis()` | Чтобы изменить, как ввод превращается в направление (геймпад и т.д.). |

```python
class DoubleJumpWithDash(PlayerController):
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.can_dash = True

    def _on_jump(self):
        self.can_dash = True   # например, восстанавливать рывок при каждом прыжке
```

## Часть 8 - Камера

### `engine/components/camera.py`

- **Ответственность:** Отслеживает виртуальную точку обзора и вычисляет
  смещение, которое `Scene.render()` вычитает из мировой позиции каждого
  спрайта, так что мир скроллится вокруг того, за чем камера следует.

```python
class Camera(Component):
    def __init__(self, target=None, follow_speed=5.0, smooth_follow=True, position=None): ...
```

| Член | Что делает |
|---|---|
| `target` | `GameObject` для слежения, либо `None` (статичный мир — см. ниже). |
| `follow_speed` | Выше = резче, при `smooth_follow=True`. |
| `smooth_follow` | `True`: плавно приближается к цели каждый кадр (см. математику ниже). `False`: точно совпадает с ней каждый кадр. |
| `set_target(target, snap=True)` | Сменить цель; `snap=True` мгновенно перецентрирует. |
| `snap_to_target()` | Мгновенное перецентрирование на текущей цели (например, после телепорта). |
| `get_offset(screen_w, screen_h)` | Мировая точка, которая окажется в верхнем левом углу экрана. **Всегда ровно `(0, 0)`, когда `target is None`** — не "что бы там ни было по умолчанию у position", а явный, безусловный ноль. |

**Камера никогда не двигает свою цель** — она отслеживает собственную
`position`, а рендер вычитает получившееся смещение из мировой позиции
*каждого* спрайта (включая саму цель). Именно это заставляет прыжки
выглядеть естественно: физика игрока совершенно не потревожена камерой.

**Математика плавного слежения** использует экспоненциальную ("smooth
damp") интерполяцию:

```python
t = 1.0 - math.exp(-follow_speed * delta_time)
position = position.lerp(target_position, t)
```

вместо более очевидного `lerp(position, target, follow_speed * dt)`.
Эффективная сила сглаживания у наивной версии зависит от частоты кадров —
при достаточно низком FPS `follow_speed * dt` может превысить `1.0`, и
камера "перелетит" цель, а затем скорректируется в другую сторону:
видимое дрожание, целиком из-за математики камеры. Экспоненциальная форма
сходится с той же *скоростью* независимо от частоты кадров и не может
перелететь цель, при любом FPS.

```python
camera_go = GameObject(name="Main Camera")
camera = camera_go.add_component(Camera(target=character, follow_speed=6.0))
scene.add_game_object(camera_go)
scene.set_active_camera(camera)
```

## Часть 9 - Система UI

Шесть небольших файлов. Позиция UI-элемента берётся из `Transform` его
`GameObject`, как и у всего остального — просто трактуется как
**экранные пиксели**, а не мировые координаты, и рисуется отдельным
проходом после мира, независимо от камеры.

### `engine/ui/ui_style.py`

- **Ответственность:** Общий набор цветов/шрифта, чтобы не повторять пять
  аргументов на каждой панели/тексте/кнопке.

```python
class UIStyle:
    def __init__(self, background_color=(60,60,70), border_color=(120,120,130),
                 border_width=2, text_color=(240,240,240), font_name=None,
                 font_size=20, hover_color=(80,80,95), pressed_color=(40,40,50)): ...
```

Не полноценный движок тем — только необходимое, чтобы было одно очевидное
место для изменения, если каждая кнопка в вашей игре должна выглядеть
иначе.

### `engine/ui/ui_element.py`

- **Ответственность:** Базовый класс для каждого UI-виджета.

```python
class UIElement(Component):
    def __init__(self, width=100, height=30, visible=True, draw_order=0): ...
```

| Член | Что делает |
|---|---|
| `rect` (свойство) | Текущий `pygame.Rect` в экранных координатах, из позиции transform'а (верхний левый угол) и `width`/`height`. |
| `contains_point(x, y)` | Проверка попадания точки, используется для hover/клика. |
| `draw_order` | Порядок **именно среди UI-элементов** (не `update_order` — отрисовка отдельный проход). Меньшее рисуется первым/снизу. |
| `draw(screen)` | Переопределяется в подклассе - вызывается `Scene._render_ui()` для каждого видимого элемента. |

### `engine/ui/ui_panel.py`

```python
class UIPanel(UIElement):
    def __init__(self, width=200, height=100, style=None, **kwargs): ...
```

Простой прямоугольный фон, опционально с рамкой.

### `engine/ui/ui_text.py`

```python
class UIText(UIElement):
    def __init__(self, text="", style=None, align="left", width=None, height=None, **kwargs): ...
```

Рисует строку; `set_text(text)` для обновления. `align`:
`"left"`/`"center"`/`"right"` (только по горизонтали — по вертикали
всегда центрируется в `height`). Ширина/высота по умолчанию равны
измеренному размеру отрисованного текста, если не заданы.

### `engine/ui/ui_button.py`

```python
class UIButton(UIElement):
    def __init__(self, text="Button", width=140, height=40, style=None, **kwargs): ...
```

| Член | Что делает |
|---|---|
| `is_hovered`, `is_pressed` | Живое состояние, обновляется из `Input` каждый кадр. |
| `on_click` | Список `callback(button)` — добавляйте через `.append()`, та же схема, что и `Collider2D.on_trigger_enter`. Срабатывает при **нажатии-и-отпускании над кнопкой** — стандартный жест кнопки; перетаскивание за пределы перед отпусканием отменяет клик. |

```python
button = button_go.add_component(UIButton(text="Старт", width=150, height=36))
button.on_click.append(lambda b: print("нажато!"))
```

### `engine/ui/ui_layout.py`

```python
class UILayoutGroup(Component):
    def __init__(self, direction="vertical", spacing=8): ...
```

`add_item(game_object)` / `remove_item(game_object)` управляют списком
UI-объектов; каждый кадр `update()` переставляет `transform.position`
каждого элемента в стек относительно позиции самого layout'а. В этом
движке нет иерархии transform'ов родитель-потомок, поэтому это *помощник*
для позиционирования, а не настоящая вложенность — но этого достаточно
для простого меню или списка HUD.

```python
layout = layout_go.add_component(UILayoutGroup(direction="vertical", spacing=10))
layout.add_item(button_a_go)
layout.add_item(button_b_go)   # автоматически позиционируется под button_a каждый кадр
```

## Часть 10 - Звук

### `engine/components/audio_source.py`

- **Ответственность:** Проигрывает звуковой эффект или зацикленный трек —
  один тип компонента для обоих случаев, как `AudioSource` в Unity
  покрывает оба.
- **Зависит от:** `pygame.mixer` (уже инициализирован через
  `pygame.init()`, который вызывает `Engine.__init__` — дополнительная
  настройка не нужна).

**Почему pygame.mixer, а не отдельная аудио-библиотека:** он уже
покрывает то, что нужно типичной 2D-игре — звуковые эффекты, зацикленная
музыка, громкость на источник, play/pause/stop — так что добавление ещё
одной зависимости было бы лишней сложностью без реального прироста
возможностей. Если вашей игре нужно что-то, что `pygame.mixer`
действительно не умеет, это единственный файл в движке, который вообще
касается звука, что делает его естественным местом для замены на что-то
другое (см. `requirements.txt`, где задокументирован этот выбор).

```python
class AudioSource(Component):
    def __init__(self, path=None, volume=1.0, loop=False, play_on_start=False): ...
```

| Член | Что делает |
|---|---|
| `load(path)` | Загружает (или заменяет) звук. Сбои (отсутствующий файл, неверный формат, нет аудио-устройства) логируются через `DebugManager`, а не выбрасываются — отсутствующий звук не должен ронять игру. |
| `play()` | Запускает с начала; безопасно с ничем не загруженным (предупреждение) или уже играющим (перезапуск). |
| `stop()` / `pause()` / `resume()` | Как названо. |
| `set_volume(v)` | 0.0-1.0. |
| `is_playing` (свойство) | Занят ли ещё лежащий в основе канал. |

```python
coin_sound = coin.add_component(AudioSource(path="assets/sfx/coin.wav", volume=0.6))
coin_sound.play()

music = GameObject(name="Music").add_component(
    AudioSource(path="assets/music/theme.ogg", loop=True, play_on_start=True)
)
```

## Часть 11 - Примитивы

### `engine/primitives.py`

- **Ответственность:** Фабричные функции, строящие готовый к
  использованию `GameObject` для простой фигуры, без обращения к
  функциям рисования Pygame напрямую.

```python
create_rectangle(x=0, y=0, width=50, height=50, color=(200,200,200),
                  name="Rectangle", add_collider=True, add_rigidbody=False, border_radius=0)
create_square(x=0, y=0, size=50, color=(200,200,200), name="Square", ...)
create_circle(x=0, y=0, radius=25, color=(200,200,200), name="Circle",
              add_collider=True, add_rigidbody=False, precise_collider=False)
create_triangle(x=0, y=0, size=50, color=(200,200,200), name="Triangle", ...)
create_line(x=0, y=0, length=100, thickness=4, color=(200,200,200), vertical=False)
```

Каждая возвращает `GameObject` с `SpriteRenderer` и (для твёрдых фигур,
если не `add_collider=False`) подходящим коллайдером — по умолчанию
ограничивающий прямоугольник `BoxCollider2D`, даже для
`create_circle`/`create_triangle` (в этом движке нет коллайдера-полигона,
и box дешевле по умолчанию для broad-phase). Передайте
`precise_collider=True` в `create_circle` для настоящего
`CircleCollider2D` вместо этого (часть 4) — только триггер/пересечение,
см. примечание об области применения в этом разделе. `create_line` без
коллайдера по умолчанию (линии обычно визуальные разделители/рельсы, не
препятствия). Ни одна из них не добавляет результат в сцену за вас.

Отдельного `create_cube()` нет — движок двумерный, поэтому предоставлен
2D-аналог (`create_rectangle`/`create_square`).

```python
platform = create_rectangle(x=50, y=450, width=400, height=40, color=(90,90,100))
scene.add_game_object(platform)

coin = create_circle(x=200, y=300, radius=12, color=(230,190,90),
                      precise_collider=True, add_collider=True)
coin.get_component(CircleCollider2D).is_trigger = True
scene.add_game_object(coin)
```

## Часть 12 - Управление миром: Scene и SceneManager

### `engine/core/scene.py`

- **Ответственность:** Владеет списком GameObject; обновляет, обрабатывает
  коллизии и рисует их. Также владеет критичными для производительности
  индексами: кэшем типов компонентов и `SpatialHash` — см.
  [Производительность](#производительность) для полной истории.

```python
class Scene:
    def __init__(self, name="Scene"): ...
```

| Член | Что делает |
|---|---|
| `game_objects` | Каждый объект в этой сцене, в порядке добавления. |
| `active_camera` | Смещение какой `Camera` применяется при рендере; `None` = чистые мировые координаты. |
| `spatial_hash` | `SpatialHash`, один на сцену. |
| `add_game_object(go)` | Устанавливает `go.scene`, добавляет, вызывает `go.start()`, инвалидирует кэш компонентов. |
| `remove_game_object(go)` | Удаляет его и очищает записи его коллайдеров в spatial hash. |
| `find_game_object(name)` | Первый объект с совпадающим `.name`, либо `None`. |
| `set_active_camera(camera)` | |
| `get_components(cls)` | Каждый компонент `cls` (или подкласса) на каждом *активном* объекте — см. [Производительность](#производительность), почему теперь это индексировано, а не линейный перебор. |
| `update(delta_time)` | Обновляет каждый активный объект, затем `_process_triggers()`. |
| `render(screen)` | `_render_world()`, затем `_render_ui()`. |

`_process_triggers()` запрашивает `spatial_hash` кандидатов broad-phase
рядом с каждым триггером, **объединяя с тем, с чем этот триггер уже
пересекался в прошлом кадре** — объединение специально гарантирует, что
`on_trigger_exit` всё равно сработает, даже если что-то сдвинулось
достаточно далеко за один кадр (телепорт), чтобы полностью покинуть
пространственную окрестность триггера, что broad-phase-запрос сам по себе
мог бы пропустить навсегда (см. тест именно для этого сценария в наборе
тестов, на котором проверялось это обновление).

`_render_world()` вычисляет смещение камеры, затем для каждого
`SpriteRenderer`: находит его исходный центр с учётом anchor, **отсекает
его, если этот центр (плюс половина исходного размера) вообще не
достигает экрана**, и иначе получает трансформированный
(повёрнутый/масштабированный) спрайт и рисует его. `_render_ui()` рисует
каждый видимый `UIElement`, отсортированный по `draw_order`, в чистых
экранных координатах.

### `engine/core/scene_manager.py`

- **Ответственность:** Владеет каждой зарегистрированной `Scene` по
  имени, отслеживает, какая активна.

```python
class SceneManager:
    def add_scene(self, name, scene): ...
    def set_active(self, name): ...   # логирует ошибку (не падение) для неизвестного имени
    def get_scene(self, name): ...
    def update(self, delta_time): ...
    def render(self, screen): ...
```

`Engine` владеет одним; `Engine.load_scene(name, scene)` — удобство для
частого случая "зарегистрировать и сразу активировать".

## Часть 13 - Диагностика: DebugManager

### `engine/core/debug_manager.py`

- **Ответственность:** Логирование (`log_info`/`log_warning`/`log_error`)
  плюс три независимых экранных оверлея: панель FPS/логов (**F1**),
  контуры коллайдеров (**F2**) и координатная сетка мира (**F3**).

Два равнозначных способа доступа, как и везде в движке, где нужна
доступность без протаскивания ссылки через каждый компонент:

```python
DebugManager.log_warning("...")     # откуда угодно
engine.debug.log_warning("...")     # через экземпляр, созданный Engine
```

```python
class DebugManager:
    def __init__(self, history_size=200, overlay_lines=8, print_to_console=True, grid_size=100): ...
```

| Член | Что делает |
|---|---|
| `log_info`/`log_warning`/`log_error(msg, source=None)` | Записывает запись с меткой времени (хранится в ограниченном кольцевом буфере) и печатает её, если не `print_to_console=False`. |
| `toggle_overlay()` / `toggle_colliders()` / `toggle_grid()` | Это вызывают F1/F2/F3. |
| `grid_size` | Пикселей мира между линиями сетки (F3), по умолчанию 100. |
| `draw_overlay(screen, scene=None)` | FPS, имя сцены/число объектов и последние строки лога, окрашенные по уровню. |

## Часть 14 - Оболочка движка: Engine

### `engine/core/app.py`

- **Ответственность:** Окно, часы, главный цикл. Единственный файл
  движка, который `main.py` должен импортировать напрямую.

```python
class Engine:
    MAX_DELTA_TIME = 0.05
    def __init__(self, width=1280, height=720, title="Pygame Engine",
                 fps=60, background_color=(30, 30, 35)): ...
```

**Цикл, каждый кадр:** измерить прошедшее время (`clock.tick`),
ограничить его `MAX_DELTA_TIME` → обработать события → `Input.update()`
→ `debug.update()` → `Scene.update(delta_time)` → очистить экран →
`debug.draw_grid()` → `Scene.render()` → `debug.draw_colliders()` →
`debug.draw_overlay()` → flip.

**Почему это ограничение:** пауза в отладчике или зависание при
перетаскивании окна могут отдать следующему кадру огромный "сырой"
`delta_time` — достаточный, чтобы быстрое тело пролетело сквозь тонкую
стену, или применить одним махом гигантский выброс гравитации.
Ограничение в 50 мс означает, что физика никогда не делает шаг опаснее,
чем "движение при 20 FPS", независимо от того, насколько долгим было
реальное зависание.

| Член | Что делает |
|---|---|
| `screen`, `clock`, `scene_manager`, `debug`, `input` | Подсистемы, которыми владеет движок. |
| `active_scene` (свойство) | `scene_manager.active_scene`. |
| `load_scene(name, scene)` | Регистрирует и сразу активирует. |
| `run()` | Блокирует, выполняя цикл, пока окно не закроется или не вызван `quit()`. |
| `quit()` | Останавливает цикл после текущего кадра. |

Клавиши: **F1** оверлей, **F2** коллайдеры, **F3** сетка (всё через
`_handle_events()`, который также обрабатывает кнопку закрытия окна).

```python

engine.run()
```

## Производительность

### Что тормозило и почему

До этого обновления проверка столкновений работала так: каждый
`Rigidbody2D`, на каждой оси, каждый кадр запрашивал у `Scene` *каждый
твёрдый коллайдер во всей сцене* (`Scene.get_components(BoxCollider2D)`,
который сам перебирал каждый GameObject). Для `n` объектов это примерно
`n` тел × 2 оси × перебор `O(n)` = **O(n²)** работы за кадр — нормально
для горстки объектов, явно роняет частоту кадров, как только сцена
достигает нескольких сотен — точно совпадает с "тормозит, когда добавляю
много объектов".

### Что изменилось

1. **`Scene.get_components()` теперь индексирован**, а не линейный
   перебор. Каждый компонент кэшируется под своим точным классом; запрос
   проходит по (небольшому) набору *различных классов*, присутствующих в
   сцене, а не по каждому объекту. Сцена с тысячей объектов, все из
   которых используют горстку классов компонентов, запрашивается так же
   быстро, как сцена с десятью объектами. Кэш инвалидируется (дешёвый
   флаг "грязный", а не пересборка) при добавлении/удалении компонента
   или GameObject, либо при изменении флага `active` у GameObject — см.
   сеттер свойства `GameObject.active` и `Scene._on_active_changed()` в
   частях 2/12.

2. **`SpatialHash`** (часть 4) распределяет коллайдеры по ячейкам
   фиксированного размера (по умолчанию 128px). `Rigidbody2D` и обработка
   триггеров теперь запрашивают "что рядом с этим конкретным rect" вместо
   "дай мне всё" — для разумно распределённых объектов это превращает
   broad-phase столкновений из `O(n²)` примерно в `O(n)` в целом.
   Поддерживается в актуальном состоянии *инкрементально* (каждый
   коллайдер сам перерегистрируется в момент обновления своей
   формы/позиции, и полностью пропускает обновление, если его
   ограничивающий прямоугольник фактически не изменился с прошлого раза —
   бесплатно для всего покоящегося), а не пересобирается раз в кадр,
   специально чтобы никогда не устаревать *внутри* одного кадра: если
   объект B уже сдвинулся раньше в этом кадре, запрос объекта A позже в
   том же кадре корректно видит новую позицию B, а не снимок с начала
   кадра.

3. **Отсечение вне экрана (viewport culling)**: `Scene._render_world()`
   пропускает любой спрайт, чей (скорректированный по anchor,
   до-поворотный) ограничивающий прямоугольник вообще не достигает
   экрана, ещё до более дорогой работы поворота/масштабирования/отрисовки.
   Сцена с тысячами объектов за пределами экрана не платит за их
   отрисовку.

### Измеренные цифры

Все измерены на одной машине (результаты будут отличаться на вашей, но
*форма* улучшения — примерно линейная, а не квадратичная — вот что
важно).

**Худший случай: каждый объект - полностью независимый, активно
падающий `Rigidbody2D`** (крайний сценарий — даже профессиональным
физическим движкам здесь нужен "сон" объектов, чтобы оставаться
быстрыми):

| Объектов (все динамические) | мс/кадр |
|---:|---:|
| 50 | 0.49 |
| 300 | 5.00 |
| 600 | 10.61 |
| 1000 | 18.36 |

**Реалистичная смесь: пара десятков активных динамических объектов
(игрок + враги) плюс тысячи статичных объектов декораций/платформ**
(вообще без `Rigidbody2D` на статичных — обычный случай для большей
части геометрии уровня):

| Статичных объектов | Динамических объектов | мс/кадр |
|---:|---:|---:|
| 200 | 10 | 0.31 |
| 1000 | 20 | 1.28 |
| 5000 | 30 | 5.44 |

Кадр при 60 FPS имеет бюджет 16.67мс. Реалистичный сценарий имеет
огромный запас даже при 5000 объектов; худший случай "всё одновременно
падает" — это та нагрузка, которая напрягла бы почти любую реализацию 2D
физики без дополнительной работы ("сон" объектов — полный пропуск
симуляции для тел, покоящихся N кадров подряд, с пробуждением только при
воздействии — стандартный следующий шаг для тех, кому реально нужны
тысячи *одновременно активных* динамических тел; это достаточно
значимая функция, со своими тонкостями корректности вокруг пробуждения
соседей, чтобы оставить её как задокументированное расширение, а не
торопиться с ней в этом проходе).

### Если ваша игра всё ещё лагает

- Не давайте статичной геометрии (платформам, стенам, декорациям)
  **вообще никакого `Rigidbody2D`** — голый `BoxCollider2D` намного
  дешевле, и это всё, что нужно статичному объекту, чтобы с ним
  сталкивались.
- Проверьте, что `cell_size` у `SpatialHash` (по умолчанию 128,
  задаётся через `Scene().spatial_hash.cell_size` сразу после создания
  сцены) не сильно не соответствует размерам ваших объектов — ячейки
  намного больше объектов означают больше кандидатов на запрос, чем
  нужно; ячейки намного меньше означают, что объект занимает (и должен
  проверяться против) больше ячеек.
- Профилируйте, прежде чем гадать дальше — `cProfile`/`pstats` на
  `Scene.update()` укажет на то, что реально медленно именно в *вашей*
  сцене.

## Anchor'ы подробно

### О чём было сообщение о баге

*«Вся эта штука с topleft/topright/center/bottom работает немного не
точно»*. Расследование этого выявило реальный пробел в дизайне — не
ошибку в математике.

### Что было на самом деле не так

Математика anchor'ов у `BoxCollider2D` сама по себе была (и остаётся)
точной — проверено для всех 9 anchor'ов против вручную вычисленных
ожидаемых позиций. Реальная проблема: **у `SpriteRenderer` вообще не
было концепции anchor** и он всегда рисовал от позиции transform'а как
верхнего левого угла, и точка. Так что в момент, когда вы задавали
коллайдеру любой anchor, кроме `"topleft"` (вполне разумно — `"center"`
совершенно естественный выбор для многих объектов), коллайдер
позиционировался правильно, пока спрайт продолжал рисоваться, как будто
ничего не изменилось — заметное расхождение между тем, где хитбокс
реально находился, и где появлялся спрайт, которое становилось *хуже*,
чем дальше выбранный anchor от `"topleft"`.

Такой же пробел существовал и у нового `CircleCollider2D` в его первом
варианте: он трактовал позицию transform'а напрямую как центр круга, без
концепции anchor, что рассогласовывало его с `SpriteRenderer`,
показывающим круг, отрисованный по центру своей поверхности (с anchor по
умолчанию).

### Исправление

Одна функция, `anchor_to_topleft_offset()` (`engine/utils/anchors.py`,
часть 1), теперь является **единственной общей реализацией**, которую
вызывает каждый класс, учитывающий anchor:

- `SpriteRenderer` получил параметр `anchor` (по умолчанию `"topleft"`,
  точно совпадает со старым поведением — никакого регресса для
  существующего кода).
- `CircleCollider2D` тоже получил параметр `anchor` (по умолчанию
  `"topleft"`, применяется к его ограничивающему квадрату `(диаметр,
  диаметр)`).

Задайте **одинаковый** anchor у `SpriteRenderer` и его коллайдера, и
теперь они точно согласованы:

```python
go.add_component(SpriteRenderer(sprite=img, anchor="center"))
go.add_component(BoxCollider2D(size=img.get_size(), anchor="center"))
# (go.x, go.y) теперь ЦЕНТР и спрайта, и его хитбокса
```

С общим значением по умолчанию (`"topleft"` у обоих) круглый спрайт,
отрисованный по центру своей поверхности, и `CircleCollider2D` по
умолчанию совпадают без какой-либо дополнительной математики смещений —
именно тот сценарий, с которого начинался этот раздел.

### Если всё ещё "не совсем то"

Две вещи, которые это исправление **не** затрагивает, потому что это не
баги anchor'ов:

- **Отступы (padding) в спрайте.** Если в исходной графике есть
  прозрачное пространство вокруг реально видимого персонажа (очень
  распространено при экспорте спрайт-листов вручную), коллайдер —
  размером с *полное изображение*, включая отступы — будет заметно
  выступать за пределы графики. Это не рассогласование между спрайтом и
  коллайдером; это истинный размер переданного вами изображения. Либо
  обрежьте графику, либо передайте явный `size=(w, h)` меньше полного
  изображения.
- **Масштаб.** `Transform.scale` отрисовывается (часть 3), но **не**
  меняет размер коллайдера — визуальное масштабирование объекта не
  меняет его хитбокс. Вызовите `set_size()`/`set_radius()` явно, если
  нужно, чтобы они соответствовали друг другу.

## Что изменилось в этом обновлении

- **Производительность**: индексированный поиск компонентов,
  `SpatialHash` broad-phase для столкновений/триггеров, и отсечение вне
  экрана для рендера — см. [Производительность](#производительность) для
  механизма и измеренных цифр.
- **Anchor'ы исправлены**: `SpriteRenderer` и `CircleCollider2D` теперь
  поддерживают ту же систему `anchor`, что уже была у `BoxCollider2D`,
  делясь одной реализацией (`engine/utils/anchors.py`) — см.
  [«Anchor'ы подробно»](#anchorы-подробно), что было не так на самом деле
  и почему.
- **Отладочная сетка F3**, наряду с уже существующими F1 (оверлей) и F2
  (коллайдеры).
- **`CircleCollider2D`** - точная проверка пересечения
  circle-vs-circle/circle-vs-box (только триггер/пересечение; см.
  примечание об области применения в части 4).
- **`AudioSource`** - звуковые эффекты и зацикленная музыка через
  `pygame.mixer`; см. `requirements.txt`, почему не добавлена
  дополнительная аудио-зависимость.
- **`load_spritesheet_animations()`** - загрузчик spritesheet + JSON-атлас,
  напрямую питающий `Animator`, поддерживающий оба распространённых
  формата JSON-атласа и корректно упорядочивающий кадры по их числовому
  индексу, а не по порядку объявления в JSON.
- **Мульти-прыжок**: `PlayerController(max_jumps=N)` для двойного/тройного
  прыжка.
- **Реструктуризация папок**: внутренности движка перенесены под
  `engine/core/`; демо полностью вынесено из движка в `examples/` (со
  своим `examples/scripts/`), чтобы граница движок/контент стала
  физической границей папок, а не просто соглашением. `engine/` никогда
  не импортирует из `examples/` — удалите папку, и движок продолжит
  работать.
- **Удалены** конкретные объекты "Player"/"Coin" из прежнего демо и их
  ассеты полностью; пример теперь использует исключительно
  `engine.primitives` (нигде в проекте нет внешних файлов изображений).
- Документация объединена в этот единственный файл (+ его английский
  перевод) вместо того, чтобы быть раскиданной по нескольким.
